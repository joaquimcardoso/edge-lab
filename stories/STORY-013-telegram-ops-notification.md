# STORY-013 — Telegram adapter, wired to daily ops status only

| Field | Value |
|---|---|
| Status | TRADING_REVIEWED |
| Owner stage | Trading Expert Agent |

## Source

The user's explicit request: Telegram "wired just to know current status." Per [docs/agents/notification-agent.md](../docs/agents/notification-agent.md) (STORY-012): Telegram is a notification sink, never part of strategy logic. Since no strategy or signal exists yet, this story wires it to STORY-009/010's already-real `DailyOpsReport`/`DayVerdict` -- not to trading signals, which don't exist.

## Goal

A Telegram sender + a pure message formatter for the daily ops status, with idempotent sends (never re-notify for a date already sent), wired into `scripts/build_daily_report.py` as an optional final step. Telegram stays fully optional -- missing credentials mean "notifications disabled," not a hard failure of the daily report job itself.

## Acceptance criteria

- [x] `src/edgelab/config.py` gains `NotificationConfig` (`telegram_bot_token`, `telegram_chat_id`, both `Optional[str]`) and `load_notification_config(*, env=None)`. `telegram_enabled` is `True` only when both are set -- missing either means disabled, never an error (this is optional infrastructure, unlike the collector's required vars).
- [x] `src/edgelab/notify/telegram_sender.py`'s `RequestsTelegramSender` wraps Telegram's Bot API `sendMessage` endpoint via `requests` (the same library STORY-008 already depends on) -- real network, never exercised in this sandbox's tests, matching every other real HTTP client in this repository (`RequestsHttpClient`, `YFinanceHistoryFetcher`). A `TelegramSender` Protocol and a `FakeTelegramSender` (records calls, no network) exist for tests.
- [x] `src/edgelab/notify/format_ops_status.py`'s `format_ops_status(report, verdict) -> str` is a pure function -- no network, no I/O -- rendering a Telegram-style message from `DailyOpsReport`/`DayVerdict` (STORY-009/010): date, verdict, today's collection counts, Gate 0 progress per source/event-type, integrity result, disk status. States plainly in the message that this is operational status, not a trading signal, and that Phase 1 (collection & audit) has no live trading.
- [x] `src/edgelab/notify/notify_ops_status.py`'s `notify_ops_status(report, verdict, *, sender, chat_id, log_dir) -> bool` sends the formatted message and returns `True`, or, if a message for `report.report_date` was already sent (checked against an append-only `<log_dir>/telegram_sent.jsonl`, same pattern as `append_heartbeat`/`append_failure_log`), skips and returns `False` without sending again -- re-running `build_daily_report.py` for the same date must never spam the same status twice.
- [x] `scripts/build_daily_report.py`'s `main()` calls `load_notification_config()` after writing the report; if `telegram_enabled`, sends via `notify_ops_status`; if not, logs plainly that Telegram is not configured and continues -- the daily report is written either way, notification is strictly additive.
- [x] `.env.example` and [08-credentials.md](../docs/08-credentials.md) document `EDGELAB_TELEGRAM_BOT_TOKEN` and `EDGELAB_TELEGRAM_CHAT_ID` (naming convention already established), noting both are obtained from Telegram's own BotFather/`getUpdates` flow, not generated by this repository.
- [x] Unit tests: `format_ops_status` against a GOOD, a WARN, and a BAD `DayVerdict`, asserting the correct verdict/reasons appear and that the "not a trading signal" disclaimer is always present; `NotificationConfig`/`load_notification_config`'s enabled/disabled branches; `notify_ops_status`'s send-then-skip-on-repeat behaviour using `FakeTelegramSender`.
- [x] System test: `build_daily_report.build_and_write` plus `notify_ops_status` composed end to end against a real report built from real stores and a `FakeTelegramSender`, asserting exactly one message was recorded and its content matches the written report/verdict.

## Explicit scope boundary

- No trading signal is ever sent -- none exists. This wires Telegram to operational status only, exactly as asked.
- No retry/backoff logic beyond what `requests` does by default -- a genuine retry policy is a reasonable future addition, not built here to keep this story's scope matched to its ask.
- Does not change `DailyOpsReport`/`DayVerdict` (STORY-009/010) -- this story only reads them.

## Definition of done

All seven gates apply, with the real-network caveat every other collector/sender in this repository already carries: `RequestsTelegramSender` itself is not exercised against live Telegram in this sandbox's tests, only via the fake.

## Credentials, if any

`EDGELAB_TELEGRAM_BOT_TOKEN`, `EDGELAB_TELEGRAM_CHAT_ID` -- both optional; their absence disables notifications rather than blocking the daily report.
